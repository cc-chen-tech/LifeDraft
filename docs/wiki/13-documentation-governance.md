# 13 - Documentation Governance

> 最后核对：2026-04-19

## 文档分层

- `README.md`：仓库入口、快速认知、链接导航  
- `docs/wiki/*`：团队长期维护知识库（架构、流程、排障、模板）  
- `docs/superpowers/plans/*`：短期计划（可变快）  
- `docs/superpowers/specs/*`：具体设计稿（方案级）

## 历史文档策略

- 历史设计/计划文档默认 **保留原文**，不删除背景信息。  
- 必须在文首标注状态（如“已落地 / 历史记录 / 最后核对日期”）。  
- 若与当前实现冲突，明确提示“以 `README.md` + `docs/wiki/*` 为准”。

## 什么时候必须更新文档

- 改 API 路径、请求响应结构  
- 改会话/状态恢复机制  
- 改 feature flag 行为  
- 改测试策略或发布流程  
- 引入新外部依赖（音乐、图像、存储等）

## 文档更新最小规则

每个涉及行为变化的 PR，至少包含：

1. 一个“受影响 wiki 页面”的更新  
2. 一段“迁移/回滚说明”  
3. 一段“验证方式”

## 文档质量标准

- 以代码现状为准，不以历史设计稿为准  
- 避免写“目标态空话”，优先写“当前路径 + 风险 + 可执行步骤”  
- 文档页内尽量包含文件/模块落点，方便跳转定位  
- 模板页保证可直接复制到 PR / ADR / 复盘中使用
