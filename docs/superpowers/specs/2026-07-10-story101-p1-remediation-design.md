# Story101 深度体验 P1 问题修复设计

> 状态：设计已批准，待书面规格确认
> 日期：2026-07-10
> 依据：Story101 生产环境深度体验（创建游戏并推进至第 4 周）
> 范围：深度 QA 报告中的 9 个 P1；每个问题独立分支、独立 PR

## 1. 背景与目标

深度体验暴露的问题不只是一组孤立报错，其中一部分共享游戏状态和叙事事实的依赖链。如果九项全部从 `main` 平行开发，会重复修改生成、恢复、存档和提示词上下文；如果全部放在一个分支，又会失去逐项审查、验证和回滚能力。

本设计采用“依赖感知的混合分支”方案：

- 每个 P1 始终对应一个独立分支和一个独立 PR。
- 不共享状态基础的修复直接基于 `main`。
- 涉及生成状态、存档恢复、事实连续性和账务一致性的修复按依赖顺序堆叠。
- 每张 PR 都有独立的红灯测试、实现、定向验证和全量回归证据。
- 好友功能不再修复 405；按产品决定删除好友入口和未使用的请求接口。

## 2. 已确认的产品决策

### 2.1 好友功能

好友问题的验收方向是“去掉”，不是“修好”：

- 删除用户可见的好友入口、按钮和相关流程。
- 删除前端未使用的好友请求客户端方法及其类型依赖。
- 删除后端只服务于该界面的好友请求路由；若仍有其他运行时消费者，先以调用证据界定最小删除边界。
- 不留下点击后报错的死入口，也不保留前后端契约不一致的半成品接口。
- 数据库表和历史数据迁移不在本轮默认范围内；仅在删除运行时代码必须迁移时纳入该 PR。

### 2.2 PR 边界

- 一张 PR 只解决一个 P1，禁止用“顺手修复”把其他 P1 混入。
- 公共基础变更只放入最早需要它的状态链 PR，后续 PR 显式依赖该分支。
- 独立 PR 不依赖未合并的状态链，确保可单独审查和合并。
- 如果根因调查证明两个 P1 无法安全拆分，先更新本设计并取得确认，不直接扩大 PR。

## 4. 总体数据与状态原则

### 4.1 权威状态优先

叙事文本是展示结果，不是角色身份、时间、健康、关系或财富的权威数据源。结构化游戏状态是唯一权威；文本输出不得反向覆盖权威字段。

### 4.2 幂等和可恢复

生成任务用稳定的操作键标识，例如 `(game_id, week, round, stage)`。重复连接和恢复请求只能附着到同一操作、读取已完成结果或返回明确状态，不能启动第二次生成。

### 4.3 原子更新

需要同时更新多个相关字段的操作先生成候选结果，完整校验后一次提交。校验或持久化失败时保留旧状态，不能写入部分空数据。

### 4.4 明确失败而非伪成功

外部服务失败必须返回结构化、可诊断且对用户可操作的失败状态。前端不得在数据为空、响应无效或任务仍在进行时记录“成功”。

## 5. 各 P1 设计与验收标准

### P1-1：生成与恢复会重启，耗时 80–120 秒

**根因假设与调查方向**

- 前端恢复路径当前可能以 `force` 再次调用生成。
- 后端以内存锁和 60 秒超时强制复位生成标志，可能在原任务仍运行时放行第二个任务。
- 页面重连、SSE 中断和阶段恢复缺少稳定操作标识和可重放状态。

**设计**

- 为一次生成定义稳定操作键和状态：`pending/running/completed/failed`。
- 同一操作键只能有一个生产者；后续请求订阅现有进度或读取最终结果。
- 恢复按钮只查询或重新连接现有操作，不发送强制生成。
- 删除基于固定 60 秒的盲目 `_generating` 复位；改为任务完成、明确失败或有证据的租约过期后清理。
- SSE 断线重连可重放必要状态，且完成事件只提交一次。

**验收**

- 并发或重复请求不会产生第二个生成任务。
- 页面刷新、SSE 断线和点击恢复不会改变操作键或重启计时。
- 已完成结果可立即恢复；失败显示可重试状态，重试创建的是明确的新尝试。
- 前端测试证明恢复路径不再调用 `generateEvent({ force: true })`。
- 后端测试覆盖两个并发连接只触发一次生成。

### P1-2：图片生成接口返回 500

**设计**

- 从 provider 配置、请求契约、超时、响应解析和持久化逐层定位首个失败点。
- 有效请求成功返回可用图片状态；缺少配置、凭据或不支持的输入返回明确的 503/422 或结构化失败结果，不泄漏内部异常。
- 对同一失败请求限制盲目重试，前端展示占位图和可恢复操作。
- 日志包含关联 ID、provider、阶段和可归类错误，不记录密钥或完整敏感提示词。

**验收**

- provider 客户端和 API 契约测试覆盖成功、超时、配置缺失、无效响应。
- 生产配置不可用时不再返回无说明的 500。
- 有凭据环境执行一次真实 smoke；无凭据时明确记录环境阻塞，不把 mock 通过等同于生产成功。

### P1-3：好友接口 405

**设计**

- 删除好友导航、个人页入口、请求/响应按钮和相关空状态。
- 删除前端好友 API 方法及仅由该功能使用的 hooks、类型和组件。
- 删除废弃的后端好友请求路由与注册；保留数据库结构除非运行时清理要求迁移。

**验收**

- 用户界面中没有好友入口或可触发好友请求的按钮。
- 前端产物不再请求 `/friends` 相关端点。
- 路由契约测试确认废弃端点不可用，且无其他页面因删除而报错。
- 全仓搜索没有仍被运行时代码引用的好友请求客户端。

### P1-4：从存档继续会自动进入下一阶段

**设计**

- 存档持久化精确阶段、当前事件标识、当前结果和待处理操作。
- 恢复时先重建保存时视图；只有状态明确表示“尚无事件且应开始生成”才允许自动生成。
- 结果页、选择页和生成中页面分别恢复，不用通用 `loading` 阶段覆盖。
- 与 P1-1 的操作状态对齐：若生成仍在进行则附着，若已完成则展示结果。

**验收**

- 在结果页保存后恢复仍显示同一结果，不推进周、轮次或阶段。
- 在选择页、生成中和失败态保存后分别恢复到对应状态。
- 恢复副作用测试证明已有当前事件时不会调用新生成。

### P1-5：人际关系重生成后数据为空

**设计**

- 重生成在临时候选对象中完成，验证人物集合、关系摘要和引用一致性。
- 只有候选结果完整有效时原子替换旧数据。
- 空数组、缺失摘要、解析失败或持久化失败都保留旧数据，并显示失败原因。
- 成功日志和 toast 只在提交完成后出现。

**验收**

- 空响应、部分响应和异常不会清空原有人际关系。
- 有效响应一次性替换人物与摘要。
- 前后端测试同时覆盖回滚、成功提示和重复点击。

### P1-6：助手幻觉污染主故事

**设计**

- 助手上下文只来自结构化角色设置、已完成事件和权威事实账本。
- 助手端点是只读查询，不直接写入故事、角色状态或账本。
- 对证据不足的问题明确表达不确定性，不补造已经发生的事件。
- 输出中若引用具体事实，校验其能在提供的上下文中定位；无法定位则重新生成或降级为不确定回答。

**验收**

- 助手无法通过回答改变游戏主状态。
- 针对不存在的人物、事件和数值，回答不会把其当成既定事实。
- 回答中的角色、日期和已完成事件与事实账本一致。

### P1-7：长期角色、日期、健康和事件漂移

**设计**

- 新增结构化事实账本，至少区分：不可变身份、时间线、已完成事件、可变健康、关系状态和事实来源。
- 每次事件生成前注入当前事实快照；生成后提取候选事实变更并校验。
- 与不可变身份或已完成时间线冲突的输出被拒绝或重试；合法的可变状态更新通过显式变更提交。
- 事实条目带来源事件和生效时间，避免只靠不断增长的全文提示词维持连续性。

**验收**

- 跨至少四周的回归场景中，姓名、年龄基准、关键日期和已完成事件不自相矛盾。
- 健康和关系可以变化，但每次变化有来源且时间顺序合法。
- 冲突生成不会覆盖权威状态，并产生可诊断记录。

### P1-8：财富和账务漂移

**设计**

- 玩家结构化数字财富是余额唯一权威来源。
- 所有选择影响以交易记录表达：期初、变动额、原因、事件来源、期末。
- 叙事不得自行声明未由交易支持的精确余额；摘要和助手统一读取结构化余额与交易。
- 生成后的数值主张与交易结果校验，不一致则纠正、重试或改写为非精确描述。

**验收**

- 每次余额变化满足 `期末 = 期初 + 变动额`，且重复提交不重复记账。
- 周摘要、角色面板、助手和故事中的精确数字一致。
- 没有交易支持时，故事不能凭空增加或减少余额。

### P1-9：危险法律建议被描述为“零风险”

**设计**

- 对法律、医疗、现实政策和规避监管类内容增加风险分类和提示词约束。
- 禁止把规避、钻漏洞或不确定行为描述为“零风险”“保证合法”“绝对安全”。
- 高风险断言在返回前经过检测；命中后重新生成、删除保证性措辞或附加明确的不确定性和专业咨询提示。
- 保持游戏叙事可玩性，但清楚区分虚构情节与现实专业建议。

**验收**

- 测试样例中的规避监管和法律边界问题不会得到零风险保证。
- 正常虚构叙事不会被无关免责声明淹没。
- 检测失败或模型不可用时采用安全降级文本，而不是原样放行高风险断言。

## 6. 错误处理与可观测性

| 场景 | 用户体验 | 系统行为 |
|---|---|---|
| 已有生成任务 | 继续显示同一进度 | 附着现有操作，不新建任务 |
| 生成失败 | 显示原因类别和明确重试 | 终止当前尝试，保留上一个稳定状态 |
| 外部图片服务不可用 | 占位图和稍后重试 | 返回结构化失败，限制重试 |
| 重生成返回空数据 | 保留旧关系并提示失败 | 候选状态丢弃，不提交 |
| 连续性或账务冲突 | 不展示矛盾结果 | 校验、重试或安全降级，记录冲突来源 |
| 高风险专业断言 | 展示不确定性或安全改写 | 检测并重写，失败时使用安全降级 |

新增日志和指标必须能够回答：一次用户操作创建了几个生成任务、恢复是否附着原任务、事实冲突发生在哪个字段、余额变更来自哪个事件、图片失败处于哪个 provider 阶段。日志不得包含凭据、完整私密故事或不必要的个人信息。

## 7. 测试与验证策略

每张 PR 统一执行以下质量门：

1. 先写能够稳定复现该 P1 的失败测试，确认红灯原因与预期一致。
2. 实施最小修复，使新增测试转绿；不在同一 PR 扩大范围。
3. 运行相关 Python、前端 Jest、契约或真实数据库测试。
4. 运行 `git diff --check` 和仓库规定的静态检查。
5. 运行 `./test.sh all`；若环境因素阻塞，分别记录代码证据和环境阻塞，不用部分通过冒充全量通过。
6. 对用户可见问题执行本地或生产浏览器 smoke，并保存关键截图、请求状态和控制台证据。

状态链还需增加一条跨 PR 场景测试：创建游戏，经历生成、保存、恢复、连续推进至少四周，并核对角色事实、事件时间线、助手回答和财富交易。

## 8. PR 交付规范

每张 PR 描述必须包含：

- 对应的 P1 编号和复现步骤。
- 根因证据，而不只是表面症状。
- 新增红灯测试及修复后结果。
- 定向测试、全量测试和浏览器验证结果。
- 是否依赖前置 PR，以及推荐合并顺序。
- 未解决的环境或生产配置阻塞。

只有当前 P1 的验收条件全部满足，才进入下一张依赖 PR。独立 PR 可交错进行，但不得共享工作树或未提交改动。

## 9. 非目标

- 不在本轮重做完整游戏架构或视觉设计。
- 不承诺仅靠提示词解决所有一致性问题；权威状态和校验必须落在代码与数据层。
- 不恢复或重新设计好友功能。
- 不删除好友历史数据库数据，除非实现删除接口时证明迁移必需。
- 不把无真实凭据的图片 mock 测试当作生产服务已恢复的证据。

## 10. 完成定义

本轮完成需要同时满足：

- 九个 P1 分别有可审查的独立 PR。
- 每张 PR 有根因、测试和验证证据，状态链依赖清晰。
- 好友功能入口和废弃请求接口已移除。
- 生成恢复和存档恢复不会重复启动或自动推进。
- 至少四周回归中，角色事实、时间、助手回答和财富账务保持一致。
- 图片和安全问题在失败时有明确、可控且不误导的降级行为。
- 全量回归结果与任何环境阻塞被分别、如实记录。
