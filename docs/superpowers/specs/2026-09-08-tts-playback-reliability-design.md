# TTS 播放可靠性设计

日期：2026-09-08。本文为完整设计提案；本次修复的实施范围、兼容性取舍和执行记录见 `docs/superpowers/plans/2026-09-08-tts-playback-reliability.md`。提案中的新进度协议、合成单元切分、WAL 和新 lease 列不属于本次故障修复，不能把本文当作这些能力已上线的声明。

白话目标：网络或数据库短暂卡顿时，已经能播放的语音继续播放；生成仍在进行时能自动恢复；用户不需要靠换音色解除卡死，也不会在不知情的情况下突然换成系统声音。

## 1. 事件证据与边界

以下来自本次对 47.250.162.194 的只读检查，时间为北京时间。

| 证据 | 结论及边界 |
| --- | --- |
| 任务 423 于 01:00:39 创建，朗读方案耗时 40.519 秒并因 truncated 降级 | AI 方案位于首段合成之前，明确拖慢首播 |
| 01:02:30 最后正常轮询；01:02:51 查询任务 423 返回 Nginx 499 | 与前端单次请求 20 秒超时一致；浏览器未上报具体 fallback 原因 |
| 01:03:01 进度写入报 database is locked，随后多个请求同时恢复 | 同步数据库操作阻塞事件循环的强证据；具体持锁事务尚未捕获 |
| 任务 423 于 01:03:10 ready；01:03:18 换音色，01:03:19 请求任务 422 的已有音频 | 后台成功与播放器恢复是两回事，换音色重置状态可掩盖故障 |
| 任务 421 的 51 段中有 39 段关联音频，失败后所有段均为 failed | 全局异常处理抹掉分段成功状态；底层 WebSocket 原因被包装后未记录 |

已核对线上后端三个核心文件与本地 SHA-256 相同，也检查了线上前端构建产物的超时和降级分支。不能把 421 的失败直接等同于用户在 423 上遇到的降级。

本设计解决已发现的故障模式；供应商不可用、浏览器后台冻结或断网仍可能发生，目标是有界等待、保存可用结果、明确反馈和可恢复。

## 2. 方案选择

| 方案 | 收益 | 局限 | 决策 |
| --- | --- | --- | --- |
| 延长轮询和数据库超时 | 改动小 | 延长静默等待，不能解决阻塞、错误降级及丢失分段状态 | 不作为修复 |
| 保留分段合成，修复执行隔离、事务、状态和恢复 | 直接覆盖本次链路，可逐层回归 | 需同时验证浏览器与数据库并发 | 推荐 |
| 迁移 PostgreSQL 并引入外部任务队列 | 提高长期并发与调度能力 | 不会自动修复前端一次失败即降级，迁移范围大 | 后续容量数据支持时另立设计 |

## 3. 必须成立的规则

1. 查询任务状态只读，不能清理任务、申请写锁或执行合成。
2. 每段音频落盘校验并提交后即可播放；后续失败、重试、租约过期不能使有效 ready 段退回 queued/failed。
3. 查询失败、合成失败、音频传输失败、浏览器禁止自动播放分别处理。
4. 更新播放进度失败不能停止音频、重建播放器或触发系统语音。
5. 系统语音由用户明确选择；后台恢复不打断正在说话的一句。
6. 同一任务只有当前租约持有者能提交结果；过期 worker 的音频不能覆盖当前结果。
7. 播放身份固定为用户、故事文本哈希、日期上下文、音色、语速及音频/方案版本。切换身份后旧请求不能修改新播放器。

## 4. 后端执行与数据库

### 4.1 把阻塞工作移出事件循环

`voice_reading.py` 中执行同步数据库或文件检查的路由改为普通 `def`，纯异步音频传输继续保留异步实现。不要只把最外层函数改成 async 后直接调用同步 helper。请求的 Session 不能传给后台合成任务；后台任务按 job_id 创建自己的 Session。

合成与拼接使用有界的专用执行器，不占用请求处理线程池。单进程默认最多同时执行 2 个合成任务；数据库保存排队状态，任务调度以数据库原子 claim 为准。预览也必须有并发上限；线程池满时任务留在队列，不向内存无限提交 Future。未来多进程部署需显式分配每进程预算，进程内上限不是集群上限。

参考：[FastAPI 对同步 I/O 路由的说明](https://fastapi.tiangolo.com/async/)。

### 4.2 短事务和真正只读的轮询

现有 `get_job()` 每次会调用 `fail_stale_processing_job()`，后者执行条件 UPDATE；即使没有过期任务，这也不是只读查询。移除该调用，过期恢复交给调度器。

worker 分为三个边界：

1. 短事务读取快照并 claim，提交并关闭 Session。
2. 不持有数据库事务地访问 MiniMax、写临时文件、校验及拼接。
3. 新建 Session，验证租约后原子提交本段资产和状态，立即关闭。

方案保存、资产失效、段状态更新均必须受租约约束。禁止在 `flush()` 后访问外部网络，禁止复用处于异常状态的 Session。锁重试重做整个短事务，不能只重试 commit；重试不得重新调用供应商。

SQLite 使用独立 TTS engine/session 配置，让 TTS 单次锁等待上限为 500ms，不改变其他业务的全局 timeout。进度接口整个数据库操作预算 1.5 秒，锁冲突最多 3 次尝试，退避 100/200ms 并受剩余预算约束。耗尽后返回结构化 503 `progress_store_busy` 和 Retry-After，不返回伪成功。任务元数据提交采用相同短等待、有限重试，耗尽后由租约恢复承接。

WAL 作为有条件的发布项：预发验证数据库位于本机持久磁盘、备份支持 SQLite 在线备份或一致快照、包含 WAL 状态，且旧业务回归通过后再切换。WAL 允许读写并行但仍只有一个写者，不能取代短事务和线程隔离。开启后监测 checkpoint 与 WAL 大小，不删除正在使用的 WAL/SHM 文件。参考：[SQLite WAL 文档](https://sqlite.org/wal.html)。

## 5. 播放器状态与恢复

从大型组件中抽取查询状态管理与进度保存；播放控件不负责判断任务是否死亡。

维护三个互不替代的状态：

- 生成：queued / processing / ready / failed，继续兼容现有接口。
- 连接：healthy / retrying / offline。
- 播放：preparing / ready / playing / paused / waiting_for_segment / failed；播放来源独立为 provider / browser。

`failed` 的生成任务仍可能有可播放段。前端先读取有效段，再决定是否有不可恢复的缺口，不能先清空队列再看到 failed 就整章降级。

### 5.1 查询失败策略

单次查询仍设 20 秒截止时间；只有一个请求在途，取消必须真实传递到 fetch 的 AbortSignal。移除 210 秒整章绝对超时即系统降级的行为，因为已经在播放的长章仍可继续生成。

| 事件 | 行为 |
| --- | --- |
| 单次网络错误、超时、5xx | 保留已知段和播放位置；1/2/4/8 秒退避，随后 10 秒间隔，加入小幅抖动 |
| 429 或 503 带 Retry-After | 尊重服务端退避，播放已有音频 |
| 连续 3 次失败或 30 秒没有成功查询 | 提示“连接较慢，正在重试”，继续等待；不切声音 |
| 页面离线 | 停止无效请求，联网后立即恢复；本地已缓冲音频可继续 |
| 页面隐藏 | 降低到 15 秒轮询；恢复可见时立即刷新，不把定时器延迟当失败 |
| 401/403 | 提示登录或权限问题；不通过系统语音掩盖错误 |
| 404 | 显示任务不存在，提供重试；不循环创建新任务 |
| 60 秒没有新增 ready 段且当前段无法播放 | 显示“正在等待语音”，可选择继续等待、重试缺失部分、系统朗读 |
| 2 分钟连接持续不可用 | 低频刷新到 15 秒，保留显式重试入口；不无限高频重试 |

健康时等待首段/下一段每 1 秒查询；已有至少两个连续可播放段时每 3 秒查询。合成心跳只表示 worker 存活，不计作新增可播放内容，不能永远掩盖音频无进展。

音频加载/解码错误只恢复当前段：重新取得该段 URL、有限重试、确认失效后请求重建该段。`NotAllowedError` 显示“点击播放”，不改成系统声音。暂停和用户拖动有最高优先级，任何迟到响应不得恢复自动播放。

### 5.2 系统语音与恢复原音色

默认不自动切系统语音；在长等待或确定缺段后显示“使用系统朗读”。用户选择后继续每 10 秒检查原任务，直到 ready、失败或离开当前故事。

原音色恢复后显示“原音色已就绪，恢复原音色”。用户点击后，在当前系统朗读段结束时从下一段恢复；不在句中切换，不估算系统语音字符进度换算成 MP3 毫秒。当前段结束后若已是最后一段则直接完成。用户主动切换音色会取消旧 utterance 和旧网络请求，并重置身份隔离标记。

播放期间优先保持分段队列；整章拼接完成不替换正在播放的 audio src。完整音频用于下次打开或停止状态下有精确时间映射的切换，避免重播与跳段。

## 6. 首播、分段容错与任务回收

### 6.1 首播路径

优先复用已校验的章节/分段音频，其次使用与文本及分段版本匹配的已持久化合法朗读方案。缺少方案时立即使用确定性合法方案开始首段合成，不在按下播放后发起额外 AI 方案请求。

现有故事生成/预生成阶段若已经产出合法方案，继续使用。显式提供但不合法的方案继续返回具体校验错误，不能静默替换。没有方案与方案非法必须区别处理。首版不新建平行 AI 方案任务，也不在生成中途替换方案；避免音色参数与缓存身份漂移。

冻结 plan_version/plan_hash 与段边界，并将其加入资产缓存身份；新方案不能命中旧方案产生的错误音频。语气仅使用现有校验允许的值。首段目标为 200–400 个中文字符，按自然句界切为合成单元，原始段落保持不变。单元维护 paragraph_index、unit_index、字符起止位置，最终时长累加映射回段落；没有句界的超长片段最多 500 字截断，记录映射。此优化在事务与恢复修复之后独立验收，不与第一阶段故障修复混做。

### 6.2 单段失败只影响单段

连接失败、接收超时、限流及供应商可重试错误：本段最多 3 次尝试，1/3 秒退避并遵循 Retry-After，总耗时受本段总预算约束。鉴权、无效音色和参数错误不盲目重试。写库失败不能被包装成供应商失败。

建议初始预算：建连 10 秒、首消息和连续无音频数据 15 秒、单段含重试合计 90 秒。接收用带 timeout 的 recv 与单调时钟总截止时间，不能仅设置 open_timeout/close_timeout；定时检查取消与 lease。预算是初始参数，需用长句和慢响应样本验证后发布。

已验证段保留 status=ready；失败段记录分类错误及尝试次数，后续未执行段保持 queued。恢复从首个缺失单元继续。拼接失败只重试拼接，所有独立段仍可连续播放。已有文件是否可复用以资产身份和音频校验为准，不单看 asset_id 是否存在。

异常日志保留异常类别、根因链、供应商状态码、协议阶段、job_id、段/单元、耗时及 attempt；不记录密钥、完整故事或音频数据。

### 6.3 独立租约与有界回收

新增 lease_id、lease_expires_at、attempt_count、next_attempt_at、last_audio_progress_at；lease_id 独立于业务 updated_at。每 10 秒续租，租约 120 秒；续租用独立短事务，不复用合成 Session。无法确认租约归属时停止提交。旧 worker 的资产绑定、方案更新和终态写入必须全部被 fencing 拒绝。

应用 lifespan 注册 TTS 调度/回收循环，数据库操作在专用线程执行；启动扫描一次，之后每 30 秒扫描到期 lease 和可执行 queued 任务，每批最多 20 条。每条使用条件 UPDATE 原子认领；调度器抢到实际执行槽后才 claim，不能让任务在执行器队列里空耗租约。两个进程扫描同一任务时只能一个成功认领。

保留有效 ready 段，过期任务最多自动恢复 2 次；超过上限持久化 failed 和 `worker_lease_expired`，显示可重试信息。正常心跳但没有音频进展的任务由单段 90 秒预算结束，不能靠心跳无限活着。关闭服务时停止认领，允许当前短事务结束，不能完成的任务由到期租约回收。旧记录以原 updated_at 和原 10 分钟规则判断，再进入新租约流程；历史无关任务超过上限终止，避免启动时批量重新计费。

## 7. API 与进度契约

保留旧 status 和字段，添加可选字段：

- `playback_state`: none / partial / complete；complete 表示所有段可播放，不要求整章已拼接。
- `ready_segment_count`、`total_segment_count`、`last_audio_progress_at`。
- `retryable`、`next_retry_at`、`assembly_state`: pending / processing / ready / failed。
- `error_code` 为稳定分类；对外 message 可读，不直接返回底层异常内容。

新客户端遇到旧响应，可由 status=ready 且 audio_url 或有效 ready segments 推导可播放性；旧响应 status=failed 的未验证段不能盲目信任。OpenAPI 与前端生成类型必须同步。

进度保存改为每 5 秒合并一次；同一播放身份只有一个请求在途，只保留最新待提交位置。暂停、跳段、结束和切换故事时尽力提交，但不阻塞播放。页面隐藏使用 keepalive 请求，不能保证关页后网络成功；未确认进度按用户与故事身份暂存本地，登出时清除，服务端确认前不能显示“已同步”。

请求增加 playback_session_id、sequence 和 expected_revision。服务端在一次条件更新中比较 revision，同会话仅接受递增 sequence；旧请求不能回滚新进度。409 时返回权威 revision，客户端仅在本地仍有未同步的新动作且播放身份未变时合并重试；重复请求幂等确认。跨标签页用 revision 冲突处理，不能拿 position_ms 最大值当新旧顺序，因为用户可以后退。存储身份增加唯一约束前先审计重复记录并制定确定性合并迁移，保留迁移备份。

## 8. 观测与验收

前端记录并上报低频状态事件：poll_timeout、poll_recovered、fallback_offered、fallback_selected、provider_ready_after_fallback、audio_waiting、audio_error、play_started、progress_sync_failed。携带随机 playback_session_id、job_id、音色、错误分类、相对耗时、媒体 readyState/networkState；不携带正文或认证信息。事件采样/限流，观测接口失败不能反向影响播放。

后端记录请求耗时、event_loop_lag、DB 锁等待/事务耗时、首段可用耗时、整章耗时、重试与 lease 回收；把接入请求 ID 传入 job 关联字段。服务器首段 ready 与浏览器实际出声分别统计，206 不能算“已播放”。

初始验收目标是测试门槛，不是尚未测得的线上 SLA：受控锁竞争下健康检查 P95 < 500ms；进度请求 1.5 秒预算内成功或结构化失败；网络恢复后一次成功轮询周期内识别原音色就绪。生产首播 P50/P95 单独采集，不能承诺供应商故障时固定秒数出声。

| 故障注入 | 必须观察到的结果 |
| --- | --- |
| 独立连接持有 SQLite 写事务 30 秒，期间同时查询任务、保存进度、请求健康检查与已有音频 | 不冻结事件循环；进度有界失败；已缓冲音频继续；锁释放后进度恢复 |
| GET /jobs 超时一次、连续超时三次，后台继续生成 | 无自动系统语音，无清空队列；恢复后接到新段，无需换音色 |
| 第 40 段失败，前 39 段已校验 | 前 39 段仍 ready/可播放，只重试第 40 段；计数和 URL 不回退 |
| 所有段成功但 ffmpeg 拼接失败 | 完整分段队列仍能播放，不重复向供应商合成 |
| 用户选择系统朗读后原音色恢复 | 展示恢复入口；点击后在段落边界切换，不双声/重读 |
| 后台完成整章时正在播放第一段 | 不替换正在播放的 src、不跳回开头 |
| AI 方案请求需 60 秒或截断；播放时缺少方案 | 播放路径不发该请求；立即进入首段合成 |
| worker 被终止；两个回收器并行扫描；旧 worker 迟到提交 | 保留 ready 段、只有一个新 owner、拒绝旧结果、重试有上限 |
| 快速切三种音色、切故事、暂停、后台标签页恢复 | 旧请求不能覆盖新身份；暂停不会被迟到响应解除 |
| 网络进度乱序、重复、跨标签页及用户向后拖动 | revision/sequence 拒绝陈旧写入，合法后退生效 |
| Safari 禁止 autoplay、音频 stalled、网络离线恢复 | 点击播放/当前段重试/恢复轮询各走对应路径，不误判供应商失败 |

数据库并发测试必须使用临时文件 SQLite 与独立线程连接，禁止共享 StaticPool；测试 DATABASE_URL 必须指向隔离测试库。锁竞争测试启动真实 ASGI 服务并发请求，不使用会掩盖事件循环阻塞的逐个 mock 调用。前端使用现有 Jest 假时钟与组件测试，浏览器使用 Playwright WebKit，并补一次真实 Safari 人工播放验证。

## 9. 文件范围与交付顺序

## 10. 设计自检结论

- 明确区分首次等待、查询异常、媒体异常和真实生成失败。
- 不把 20 秒改成更长时间充当修复；也不以 WAL 消除所有写锁为前提。
- 包含部分成功、拼接失败、旧 worker、乱序进度、暂停与手动降级的恢复语义。
- 参数标为初始配置，性能目标标为待验证门槛；供应商根因及原始持锁事务仍需运行时观测补全。
- 本次交付仅设计文档，未修改应用代码及生产配置；工作区原有 nginx/ecs-nginx.conf 修改不属于本设计交付。
